## 4. 端到端流程完整性

## 4.1 已经覆盖的流程

当前项目已经覆盖一部长篇小说的大部分生命周期：

```text
安装插件
  ↓
初始化书项目
  ↓
拆样板书与确定边界（可选）
  ↓
世界观 / 力量体系 / 角色 / 正典
  ↓
总纲 → 卷纲 → 细纲 → 伏笔表
  ↓
写前接地
  ↓
章节起草 → 自查 → 润色 → 连续性复查
  ↓
状态、账本、中央面板回写
  ↓
机检闸门
  ↓
质量审查
  ↓
作者确认
  ↓
下一章 / 阶段审查 / 发布导出
```

其中设计较好的部分包括：

1. **文件是事实，会话是缓存**：避免依赖超长聊天上下文；
2. **正典与账本分层**：`canon.md` 管易错事实，`ledger.tsv` 管跨章数值；
3. **写前接地**：降低模型凭印象续写的概率；
4. **机器检查与人工评审分离**：可计算问题进入闸门，主观质量留给 `/review`；
5. **每章一停**：给作者保留人工审批权；
6. **配置项目化**：不同小说的专有值进入 `book.json`，通用脚本保持共享。

## 4.2 尚未真正闭环的部分

| 环节 | 当前状态 | 缺口 |
|---|---|---|
| 初始化 | 有完整骨架生成 | 写入不是事务性的，可能覆盖已有配置 |
| 写前接地 | 能汇总大纲、正典、账本和状态 | 缺关键输入时仍返回成功 |
| 流程留痕 | 有格式约定 | 只验证“存在”，不验证“内容有效” |
| 批量长跑防护 | 有校验点 | 只警告不拦截，随后还会推进校验点 |
| 章节连续性 | 有最大章号 | 没有核对准确章号集合 |
| 状态一致性 | 有状态块和哈希基线 | 多进程写入无锁、无原子替换 |
| 多书并行 | 各书数据目录隔离 | 无法定位时会猜最近修改的书 |
| 版本控制 | 有完整文档 | 初始化脚本没有真的执行 Git 初始化 |
| API 安全 | 密钥放在 `.env` | 初始化未确保 `.env` 被 Git 忽略 |
| 自动检查 | Hook + Watcher 双入口 | 重复扫描、共享报告竞争、可能并发踩写 |

因此更准确的评价是：

> **创作流程完整，工程事务不完整；规则写得严，执行代码仍有绕过路径。**

## NW-P0-001：初始化和同步可能覆盖已有文件

### 位置

- `scripts/init_book.py:241–304`
- `scripts/sync.py:331–348`
- `scripts/sync.py:407–411`

### 当前行为

`sync.plan()` 把以下文件视为完整生成物：

- `AGENTS.md`
- `tools/*.py`
- `.zcode/config.json`
- `.codebuddy/settings.json`

`do_book()` 对生成物直接使用写模式覆盖。初始化脚本也会把规划结果无条件写入书目录。

另外，`init_book.py --force` 会重新写入：

- `.soloent/book.json`
- `.soloent/canon.md`
- `.soloent/ledger.tsv`
- `.soloent/memory/now.md`
- `SOLOENT.md`
- 其他模板文件

但没有自动备份、变更预览或事务回滚。

### 已验证复现

1. 在待初始化目录创建 `.codebuddy/settings.json`；
2. 写入与本插件无关的自定义字段；
3. 运行 `init_book.py`；
4. 自定义字段消失。

### 影响

- 覆盖用户的编辑器、插件或其他 Hook 设置；
- `--force` 误用可能抹掉长期积累的正典、账本和当前状态；
- 中途异常可能留下“配置已更新、模板只更新了一半”的半初始化项目；
- 如果没有 Git，恢复成本很高，甚至无法恢复。

### 建议修复

1. `.codebuddy/settings.json` 和 `.zcode/config.json` 改为结构化合并：
   - 只维护本插件拥有的 Hook 节点；
   - 保留所有未知字段；
   - 发现非法 JSON 时拒绝覆盖。
2. 所有重要写入使用：
   - 同目录临时文件；
   - `flush`；
   - 原子 `replace`。
3. `--force` 执行前生成：
   - `.soloent/backups/<时间戳>/`；
   - 覆盖清单；
   - 原文件哈希。
4. 初始化采用两阶段提交：
   - 第一阶段构造全部目标内容并验证；
   - 第二阶段统一替换；
   - 任一步失败则不改变现有书项目。

### 验收标准

- 已有设置文件的未知字段在 init/sync 后仍然存在；
- 非法 JSON 不会被覆盖；
- `--force` 前必定生成可恢复备份；
- 模拟中途异常后，项目不会处于半更新状态；
- 对同一配置重复执行 sync 具有幂等性。

## NW-P1-002：流程留痕可以伪造

### 位置

- `scripts/preflight.py:93–125`
- `scripts/preflight.py:204–210`

### 当前行为

当前正则只要求一行以以下内容开头：

```text
[流程] ch-N
```

之后的文本没有进行严格解析。因此：

```text
[流程] ch-1 任意文本
```

也会被视为有效留痕。

即使尾部明确包含“未执行、跳过、未跑”，`flow_trace()` 返回的状态也只会进入警告，不会进入拦截。

### 影响

项目反复强调的四步工艺：

- 句法自查；
- 技能三连；
- 连续性复查；
- 收尾回写；

实际上没有被闸门可靠约束。Agent 忘跑、糊弄或格式写错时仍可能继续下一章。

### 建议修复

最低限度使用完整格式校验：

```regex
^\s*\[流程\]\s*ch-?0*(\d+)\s+自查(\d+)\s+三连(\d+)\s+复查(\d+)\s+回写OK\s*$
```

进一步建议改为机器生成凭证：

```json
{
  "chapter": 31,
  "syntax_review": {"completed": true, "fixed": 4},
  "skill_chain": {"completed": true, "fixed": 7},
  "continuity_review": {"completed": true, "fixed": 1},
  "writeback": {"completed": true},
  "chapter_sha256": "...",
  "completed_at": "2026-09-19T12:00:00+08:00"
}
```

正文修改后，正文哈希与凭证不一致时，凭证自动失效。

### 验收标准

- 任意文本不能通过；
- 缺少四个字段中的任何一个都不能通过；
- “跳过、未跑、未执行”必须拦截；
- 修改正文后旧流程凭证必须失效；
- 流程凭证的章节号必须与实际最新章一致。

## NW-P1-003：闸门存在多处失败放行

### 位置

- `scripts/preflight.py:139–150`
- `scripts/preflight.py:174–190`
- `scripts/preflight.py:192–210`
- `scripts/preflight.py:231–237`

### 问题 A：未匹配正文被当作“没有章节”

当 `book.max_chapter()` 返回 0 时，闸门会提前返回通过。

如果 `chapters/` 里已经有正文，但文件名不符合 `chapter.file_regex`，这些文件不会被纳入 `max_chapter()`，最终仍然显示：

```text
结果：✅ 通过（无章节可校验）。
```

### 问题 B：状态或账本脚本缺失时不拦截

`consistency_check.py` 缺失会加入 blocker，但 `state_sync.py` 和 `ledger.py` 缺失时只显示“未接入”，没有进入 blocker。

这违反了“抓不到结果一律失败关闭”的设计原则。

### 问题 C：批量长跑只警告

当：

```text
当前最大章号 - 上次校验章号 >= batch_warn
```

系统只添加警告。没有其他 blocker 时，闸门仍然成功，并把校验点直接推进到当前最大章号。

这会把“5 章没有逐章验证”压缩成“第 5 章已经验证”，历史信息永久丢失。

### 建议修复

1. 在任何提前返回之前检查：
   - `chapters/` 是否存在 Markdown 文件；
   - 是否有未匹配文件；
   - 是否存在重复映射章号。
2. 三个核心子检查只要任何一个缺失、超时、异常、无结构化结果，都必须拦截。
3. 校验点不能只存单个最大章号，至少应保存：
   - 每章正文哈希；
   - 每章通过时间；
   - 每章检查版本。
4. 如果新增多章：
   - 逐章补跑；或
   - 直接拦截，要求从 `last + 1` 开始补验。
5. 未匹配的正文文件应定为严重问题，而不是中等提示。

### 验收标准

- `chapters/` 有未匹配 Markdown 文件时闸门失败；
- 任一核心子脚本缺失时闸门失败；
- 任一子脚本超时或输出格式错误时闸门失败；
- 一次新增多章不能通过单次检查直接推进校验点；
- 校验点能够回答“哪一章在什么正文哈希下通过了检查”。

## NW-P1-004：正文与账本没有集合级核对

### 位置

- `scripts/kit.py:156–195`
- `scripts/ledger.py:180–201`
- `scripts/state_sync.py:163–165`

### 当前行为

核心逻辑大量依赖“最大章号”：

- 正文最大章号；
- 账本最后一行章号；
- `now.md` 声明章号。

账本缺口检查只比较账本自身的第一条到最后一条。如果账本第一条就是第 5 章，则：

```text
got = [5]
range(got[0], got[-1] + 1) = [5]
```

系统会认为没有缺口。

### 已验证复现

- 正文：第 1、2、3、4、5 章；
- 账本：仅第 5 章一行；
- `ledger.py --quiet` 返回成功。

### 还可能遗漏的情况

- **ch-1.md** 与 **ch-01.md** 同时映射为第 1 章；
- 正文存在第 1、3 章，但第 2 章缺失；
- 账本有第 2 章，但正文第 2 章已经删除；
- 文件名符合正则，但标题写成另一章；
- 正文章号连续，账本章号连续，但两者集合不同。

### 建议修复

建立统一的章节索引：

```python
chapter_files_by_number: dict[int, list[path]]
ledger_rows_by_number: dict[int, list[row]]
```

然后验证：

```text
正文章号集合 == 账本章号集合 == {1, 2, ..., 当前章}
```

并增加：

- 重复正文章号；
- 重复账本章号；
- 正文缺章；
- 账本缺章；

## NW-P1-005：“直接写第一章”与强制前置阶段冲突

### 位置

- `docs/00-总览与流程.md:21–55`
- `scripts/init_book.py:12`
- `scripts/brief.py:197–251`

### 矛盾内容

一组文档允许：

```text
先写第一章 —— 已有想法，边写边补设定
```

另一组文档明确声明：

世界观、总纲、卷纲、细纲不可跳过；

### 验收标准

- 正式模式缺细纲时 `brief.py` 返回非零；
- 正式模式缺正典时返回非零；
- 探索草稿不能被 `preflight.py` 当作正式章节；

## NW-P1-008：Hook/Watcher 重复扫描且并发写入无锁

### 位置

- `hooks/after_chapter_write.py:67–68`
- `scripts/watch_and_check.py:117–128`
- `scripts/preflight.py:154–190`
- `scripts/consistency_check.py:409–414`
- `scripts/kit.py:304–389`
- `scripts/state_sync.py:77–81`

### 当前调用链

章节保存 Hook：

```text
consistency_check 全量（无 tag）
  ↓
preflight
  ↓
consistency_check 再次全量（无 tag）
state_sync
ledger
```

Watcher 的直接 consistency 使用 `--tag watch`，会写入独立报告；但它随后调用 preflight，
preflight 内部再次运行无 tag consistency。手工运行 preflight 也走同一路径。因此以下入口仍共享
无 tag 的**当日对账报告**：

- Hook 的直接 consistency；
- Hook 内部 preflight 发起的 consistency；
- Watcher 内部 preflight 发起的 consistency；
- 手工运行 preflight 发起的 consistency；
- 手工直接运行、且没有指定 tag 的 consistency。

另外，`consistency_check.py` 已经提供 `--since N`，但 Hook 和 Watcher 当前都没有使用它。

### 影响

1. 每保存一次正文，至少扫描全书两遍；
2. 无 tag 报告可能被 Hook、Watcher 内部 preflight 和手工命令同时重写；
3. `对账趋势.csv` 虽已同日覆盖和去重，但仍是无锁的“读全表 → 改写 → 重写全表”，
   并发时可能丢失更新或留下不完整文件；
4. `state_hashes.json`、报告 Markdown、趋势 CSV 均无进程锁或原子替换；
5. 长篇达到数百或上千章后，30 秒 Hook 超时概率上升；
6. 自动检查超时后，用户可能只看到 Hook 静默失效。

### 建议修复

1. `preflight.py` 成为唯一编排入口；
2. 增加 `--json` 输出，返回每个子检查的结构化结果；
3. Hook 和 Watcher 不再预跑 consistency，并把入口 tag 传给 preflight，再由 preflight 传播给子检查；
4. 把现有的 `--since N` 接入自动入口：
   - 当前变更章或最近 1 章做正文检查；
   - 全量账本做跨章检查；
   - 定期或手工运行全量正文检查。
5. 使用项目级锁：

```text
.soloent/locks/preflight.lock
```

6. 报告和状态文件使用原子替换；
7. 保留趋势文件现有的同日覆盖与历史去重逻辑，并把整个读改写过程纳入项目锁。

### 验收标准

- 一次章节保存只执行一次正文检查；
- Hook 与 Watcher 同时触发时只有一个检查进程工作；
- Hook、Watcher 与手工入口不会无保护地重写同一个报告；
- 趋势 CSV 并发写入时不会丢失更新或产生无效 CSV；
- 中途终止不会产生半截 JSON 或半截 Markdown；
- 1000 章模拟项目的自动检查时间有明确预算和基准。

## 7. 推荐的目标架构

## 7.1 章节状态机

建议为每章建立显式状态：

```text
planned
  ↓
drafted
  ↓
self_checked
  ↓
continuity_checked
  ↓
state_written_back
  ↓
preflight_passed
  ↓
quality_reviewed
  ↓
author_approved
  ↓
published
```

只有 `author_approved` 才允许开始下一章。

状态记录应包含正文哈希。正文变化后，后续状态自动回退到 `drafted`，不能继续沿用旧审查结论。

## 7.2 单次章节事务

目前一章完成涉及多个文件：

- 章节正文；
- `now.md`；
- `ledger.tsv`；
- `SOLOENT.md §7`；
- 流程留痕；
- 校验点；
- 状态哈希。

建议增加章节事务清单：

```json
{
  "chapter": 31,
  "chapter_file": "chapters/ch-31.md",
  "chapter_hash": "...",
  "now_hash": "...",
  "ledger_hash": "...",
  "soloent_hash": "...",
  "status": "preflight_passed"
}
```

任何相关文件变化，都能判断哪些审查结果已经失效。

## 7.3 结构化检查协议

不要再由上层脚本解析下层脚本的中文输出，例如：

```text
严重 0 · 中等 2 · 轻微 9
```

建议所有工具支持：

```bash
python tools/preflight.py --json
```

输出固定结构：

```json
{
  "ok": false,
  "chapter": 31,
  "blockers": [],
  "warnings": [],
  "checks": {
    "consistency": {"ok": true, "counts": {}},
    "state": {"ok": true},
    "ledger": {"ok": false},
    "flow": {"ok": true}
  }
}
```

控制台文本只作为展示层，JSON 才是程序契约。

## 7.4 安全写入层

所有状态文件统一经过一个写入模块：

- 项目根路径约束；
- 备份；
- 临时文件；
- 原子替换；
- 进程锁；
- 哈希校验；
- 失败回滚。

这样可以避免每个脚本各自实现一套不完整写入逻辑。

## 11. 最终结论

这个项目已经具备较成熟的长篇创作方法论，尤其是：

- 正典速查；
- 写前接地；
- 跨章账本；
- 状态回写；
- 机器闸门与人工质量审查分离；
- 每章人工确认；
- 多阶段文档化流程。

它当前的问题不是”缺少流程”，而是：

> **流程已经写全，但关键纪律尚未全部变成不可绕过的程序约束。**

优先完成 P0/P1 修复后，它可以成为可靠的个人长篇创作工具。进一步补上事务、锁、结构化协议、生成溯源和成本观测后，才适合向多书并行、长期自动运行或多人协作方向扩展。

### 12.3 遗留风险

1. **依赖分层未单独成文（NW-P2-010）**：核心工具仍为纯标准库；拆书摘要（openai）与封面生成（Pillow）的依赖说明未正式分层。影响：可选功能运行时才发现缺依赖。
2. **1000 章性能基准未建**：preflight 已支持 `--since` 增量与锁，但自动检查时间预算尚无大规模基准数据。`chapter_files()` 全量读文件的做法在超长篇下仍有优化空间。
3. **复杂位置数组未改为具名对象**：`gated_keywords`、`locked_details`、`rank_costs` 等仍依赖固定位置；结构校验只覆盖骨架键，不校验业务数值结构。
4. **锁的适用范围**：项目锁覆盖 preflight 编排与报告/趋势/哈希写入；watcher 的 `对账日志.md` 追加写依赖 O_APPEND 原子性，未持锁（小写入，风险低）。
5. **doctor 对「配置无效」的书**提示文案仍为「book.json 读不出来」，未区分「缺失」与「校验未通过」。

### 12.4 结论更新

> 第一阶段（阻止数据损失和假通过）与第二阶段（可靠性与并发）的主体任务已完成并有回归测试锁定；第三阶段（生成溯源、成本预算、质量看板、正典双向同步、release gate）尚未开始。插件已可用于**单人长期自动连载**，多书并行场景在「从具体书目录启动会话」的约束下是安全的。
